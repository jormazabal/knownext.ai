# Avance93 · Reunir historiales que ya contienen los mismos archivos

[Reporte visual](avance-93.html).

F06/T02/T03/U09: primera publicación real del grafo de divergencia, limitada a dos historiales cuya totalidad de archivos registrados coincide exactamente. Revisión local y referencia remota conocida, sin fetch ni push. El usuario revisa y confirma Reunir historiales; Rust crea una versión con el árbol común y ambos padres. No hace checkout ni actualiza el índice o los documentos. Borradores privados conservados. Diferencias de contenido, cambios de archivos sin registrar, revisión antigua, falta de referencia local activa o catálogo no revisable impiden la acción. La interfaz no muestra nombres de ramas.

Publicación mediante transacción Git update-ref que compara las identidades completas local y remota antes de actualizar únicamente la referencia local capturada. HEAD, raíz y configuración de origen se revisan antes/después; no son CAS contra programas Git externos. Un resultado no comprobable no se presenta como éxito. La primera variante intentaba verificar también HEAD en la transacción: Git2.51 rechaza la doble actualización implícita de HEAD. Se corrigió el protocolo y se repitieron solo los contratos afectados. No existe fallback a una publicación sin comparación.

Se crea primero un recibo inmutable formato1 con intento criptográfico, revisión, raíz/origen, referencias privadas, árbol, padres y versión preparada. El ID queda ligado también al mensaje de esa versión; un intento posterior que produzca los mismos archivos crea una identidad diferente. Acuse perdido: una consulta automática del mismo ID, ningún reenvío; not-started no consulta. El catálogo permite consultar al reabrir UI sin el pedido RAM original. Preparación no equivale a publicación. La consulta verifica el objeto, sus padres/árbol/intento y la referencia actual; pending/changed/absent no autorizan reanudar ni reparar.

Catálogo por proyecto:64 recibos,16KiB por registro, hasta1MiB y2s cooperativos de lectura. Deserialización estricta, fecha/identidad/rutas conocidas, carpetas/archivos regulares sin enlaces. Futuro, desconocido o ilegible se conserva y provoca parcialidad; no se poda ni reciclan IDs para liberar capacidad. En capacidad o catálogo parcial la acción aparece deshabilitada desde la revisión. La retención global de identidades sigue abierta. La transacción de referencias espera como máximo10s; las consultas Git previas mantienen sus límites de salida existentes y aún no tienen un plazo duro general. Hooks desactivados para esta publicación, sin firma GPG interactiva, sin proceso auxiliar de producto. Referencias primarias: [commit-tree](https://git-scm.com/docs/git-commit-tree), [update-ref](https://git-scm.com/docs/git-update-ref).

UI: confirmación explícita con alcance local, recibo y consulta independientes del resultado anterior. Los controles de consulta/cierre permanecen en el pie en320px. Tras un éxito se etiqueta la lista previa como revisión anterior; una revisión nueva muestra el estado nuevo. Error o incertidumbre conserva el intento, sin ofrecer otro envío automático. Las preparaciones del catálogo no se presentan como éxitos.

Contrastes: cuatro casos Rust nuevos en carpetas temporales propias: publicación con ambos padres y conservación exacta de archivo/índice/borrador/hook; rechazo de revisión obsoleta, archivo pendiente y árboles distintos; corte representado por recibo preparado, intento posterior que no confirma al anterior, futuros preservados; capacidad64 sin poda. Cinco casos frontend nuevos entre SDK/diálogo. TypeScript correcto. Prueba de conservación usa reapertura real de LocalApi; corte de preparación se modela en el fixture, no matando el proceso instalado.
