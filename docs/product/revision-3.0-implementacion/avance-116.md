# Avance116 · Retirada de copias de conflictos con respaldo íntegro

[Reporte visual](avance-116.html) · [Plan](plan.md).

F04/F06/F07/F17/T02: recibos completados y archivados ofrecen respaldo completo y retirada local. El ZIP contiene los bytes exactos de cada copia JSON y sus manifiestos, además de Documentos.zip, importable como proyecto nuevo mediante el flujo existente. Es un respaldo privado con metadatos locales; compartir variantes conserva su flujo distinto. No se exporta el almacén de credenciales ni la configuración de ejecución. Los recursos vinculados ajenos a las copias y el estado integral del proyecto quedan fuera. Hasta32MiB de datos completos y40MiB por ZIP; no se entrega un conjunto parcial por exceso de tamaño.

Retirar exige revisión vigente, confirmación y elección nativa del ZIP completo en cada intento. Se comprueban tamaño/SHA de todos sus bytes antes de crear un diario inmutable y antes del primer unlink. Solo se retiran representaciones conocidas copy.json/copy.json.zip verificadas; permanecen recibo, manifiestos e identidad. El diario conflict-retirements/<id>.json formato1 conserva huellas del recibo, respaldo y representaciones. Generación monotónica evita reutilizar revisiones anteriores; no se liberan cuotas de identidades.

Cortes dejan estado retiring o retired consultable, sin continuación al leer. Reintentar requiere revisión nueva y elegir/comprobar el ZIP otra vez. Formato futuro, extras, enlaces, bytes/metadatos cambiados o solo lectura preservan lo restante. No se reabre ni compacta un recibo con retirada iniciada. Recuperación muestra esa fase y el recibo archivado, sin sugerir repetir el intento ni tratar la retirada como corrupción. Windows usa selector nativo; Android reutiliza SAF, pendiente de su compilación/aceptación.

La validación detectó puertas globales que podían marcar como ocupado otro almacén. Retención y revisiones monotónicas ahora admiten por ruta canónica de almacén con registros débiles; no esperan entre operaciones del mismo almacén ni retienen referencias a perfiles ya cerrados. Un contrato concurrente público hace ocho ciclos compactar/expandir en dos perfiles con el mismo intento, conservando bytes y manifiestos.

Verificación dirigida: dos contratos Rust nuevos pasan (respaldo/retirada y perfiles independientes). Dos contratos de inventario afectados y el caso de retención que falló pasan tras la corrección; se reutilizan las comprobaciones de códecs no modificados. El contrato de retirada verifica JSON exactos en ZIP, paquete documental anidado, archivo erróneo/sin confirmación, corte por solo lectura, estado tras consulta, rechazo de revisión anterior/futuro/extras, continuación, recibo/manifiestos/ZIP/documento/borrador intactos e intento no repetible. Seis casos frontend/SDK y TypeScript final correctos. Registro de los dos comandos nuevos y compilación Tauri Windows correctos. No se ejecutan suites completas.
