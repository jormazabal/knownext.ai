# Avance95 · Recuperar el recurso histórico en un archivo nuevo

[Reporte visual](avance-95.html).

F04/F05/F06/T02/T03/T08/T14: desde la revisión de proyecto se puede recuperar una entrada regular local o remota conocida como archivo nuevo, también recursos binarios y versiones anteriores a una eliminación. La lectura queda vinculada a revisión completa del grafo, ruta/lado, commit/blob y SHA de los bytes. No hay fetch, checkout, proveedor ni incorporación automática de la variante a otra ruta. En una eliminación se toma la base común revisada y se identifica como versión anterior; no se inventa contenido a partir del archivo actual. Enlaces, submódulos y cambios de tipo no admitidos se rechazan.

El usuario elige un nombre en la raíz del proyecto, con extensión conservada. Rechaza nombres ocupados, equivalentes por caso/normalización o no portables; no convierte formatos ni sobrescribe originales. La copia puede moverse después con el flujo existente. Se obtiene el blob regular de Git sin filtros de contenido y con límite32MiB. Vista textual de Markdown/TXT/CSV limitada4000 caracteres y truncamiento visible; otros formatos conservan bytes completos sin prometer vista textual. No se muestran nombres de ramas.

La preparación y recibo1 se conservan en .knownext-history-copies, almacén privado de proyecto con propietario1 estricto y .gitignore conocido. Se inicializan propietario/ignore completos antes de publicar la carpeta, sin reclamar ni reparar una carpeta ajena/futura. Ruta y preparaciones reservadas en path_policy, ocultas del árbol e índices y excluidas de paquetes de archivos. Uso se clasifica en recuperación y sigue siendo contabilidad lógica: un enlace puede contar más de una vez. La primera integración situó la preparación en .knownext-runtime y la protección de coordinación la rechazó; se separó el almacén sin relajar esa protección y se repitieron solo los dos contratos afectados. No se han migrado datos de un perfil real por este cambio.

La publicación usa un enlace físico nuevo desde un ancla privada ya vaciada a disco. El recibo liga ID criptográfico, fuente, nombre, bytes e identidad física de esa ancla; la consulta exige mismo objeto, SHA y ubicación. Windows usa FILE_ID_INFO de128bits/volumen; Unix dev/inode no nulo. Un archivo ajeno con los mismos bytes o el publicado por otro intento no confirma el primero. Un acuse incierto provoca una sola consulta del mismo ID y ningún reenvío. Las consultas no reanudan ni reparan. Sistema sin enlace/identidad comprobables falla conservando la preparación, sin fallback de copia o reemplazo. El ancla enlazada es una referencia de identidad, no se presenta como otro respaldo inmutable: una edición en el mismo objeto puede alterarla y entonces no se confirma el resultado actual. La versión fuente de Git no se reescribe.

Límites:32MiB por recurso, recibo16KiB,64 copias/128MiB por proyecto,130 entradas de inventario y2s cooperativos. Pareja incompleta, futuro o entrada desconocida conserva contenido y declara parcialidad; no se permite otra copia ni se podan IDs para liberar cuota. Hash/identidad de archivos se leen con búfer64KiB y5s cooperativos por lectura. El blob inicial aún ocupa hasta32MiB; no es una cuota dura del proceso ni una garantía de latencia/memoria de Git. No se inspeccionan ni eliminan archivos de bloqueo. Referencias primarias: [enlaces físicos Rust](https://doc.rust-lang.org/std/fs/fn.hard_link.html), [identidad de archivo Windows](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getfileinformationbyhandle).

UI con revisión, nombre y acciones fijas. Campo y recibo se conservan tras error; otra decisión exige revisión exitosa y mantiene el nombre elegido.
